The engine can enforce OIDC JWT validation on agent API routes. When SSO is enabled, clients must present a valid JWT in the `Authorization` header to call `/agent/*` endpoints.

This page covers route protection for the engine runtime. For standalone admin-panel auth (the `idun_session` cookie on `/admin/*`), see [Standalone overview](/standalone/overview) and [Deployment hardening](/deployment/hardening).

## Protected routes

When SSO is enabled, every `/agent/*` route requires a valid bearer token. The canonical AG-UI entry point is:

- `POST /agent/run`

The following routes are deprecated compatibility shims, also gated by the same SSO dependency:

- `POST /agent/invoke`
- `POST /agent/stream`
- `POST /agent/copilotkit/stream`

Health and metadata routes (`/health`, `/_engine/info`) stay open. The engine `/reload` route is not currently gated by the SSO dependency; treat the engine as a process running inside a trusted boundary.

## Configuration

<Tabs>
  <Tab title="YAML">
    Add an `sso` block to your engine `config.yaml`:

    ```yaml config.yaml
    sso:
      enabled: true
      issuer: "https://accounts.google.com"
      client_id: "your-oauth-client-id"
      audience: "your-oauth-client-id"
      allowed_domains:
        - "company.com"
      allowed_emails:
        - "admin@partner.com"
    ```

    | Field | Description |
    |---|---|
    | `enabled` | Toggle SSO enforcement on protected routes |
    | `issuer` | OIDC issuer URL. Used to discover the JWKS endpoint via `.well-known/openid-configuration` |
    | `client_id` | OAuth 2.0 client ID. Used as the default audience for JWT validation |
    | `audience` | Expected JWT `aud` claim. Defaults to `client_id` if not set |
    | `allowed_domains` | Optional list of allowed email domains (e.g. `["company.com"]`) |
    | `allowed_emails` | Optional list of specific email addresses allowed access |
  </Tab>
  <Tab title="Admin UI">
    In the standalone admin panel, navigate to the agent's SSO settings, paste the issuer URL, client ID, and any domain or email allowlists, then save. The standalone reload pipeline validates the config and re-instantiates the engine with the new SSO settings.

    ![SSO page](/images/ui/sso-page.png)
  </Tab>
</Tabs>

## Supported providers

Any OIDC-compliant provider works as long as it publishes a JWKS endpoint via `.well-known/openid-configuration`. Tested providers:

- **Google Workspace** (issuer: `https://accounts.google.com`)
- **Microsoft Entra ID / Azure AD** (multi-tenant via `https://login.microsoftonline.com/common`, or single-tenant via `https://login.microsoftonline.com/<tenant-uuid>`)

<Note>
  Domain and email allowlists are applied after JWT signature verification. A valid token from an allowed provider is still rejected if the email domain or address is not in the allowlist.
</Note>

## How validation works

1. The engine discovers the JWKS endpoint from the issuer's `.well-known/openid-configuration` document at startup.
2. For each request to a protected route, the engine reads the `Authorization: Bearer <jwt>` header.
3. The JWT signature is validated against the JWKS. Signature algorithm and key are taken from the JWT header.
4. The `aud` and `iss` claims are matched against `audience` and `issuer` from your config.
5. If `allowed_domains` or `allowed_emails` is set, the token's `email` claim is checked against the lists.
6. On success, the request proceeds. On failure, the engine returns `401 Unauthorized`.

Tokens are not stored or persisted. Each request is validated independently.

## Calling a protected agent

Obtain a JWT from your provider, then pass it in the `Authorization` header:

```bash
# Export the JWT obtained from your provider's OAuth flow
export JWT=$(your-token-tool fetch)

curl -X POST https://your-agent.example.com/agent/run \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{
    "thread_id": "test-1",
    "messages": [{"role": "user", "content": "Hello"}]
  }'
```

For browser clients, obtain the token through your provider's standard OAuth 2.0 + PKCE flow, then call the agent API from your application code with the resulting access token.
